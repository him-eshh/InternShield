## Why v3 exists (the owner's verdict on v2, Oct 25, 2026)
He tested v2 by hand. The scoring logic works. Everything else fell short: the tailored resume was too long, lost the original format and read as AI-written ("it will get rejected"); no loading state, no preview before download, no way to adjust and see changes. No nav bar, no home screen, no profile screen, no icons; very hard to navigate; unclear how to build the profile; flows dropped him back into the questions. Answers/details he added showed no visible effect ("no score impacted" is a dead end). The UI looked basic and AI-generated, only black and blue, unresponsive, no motion. The interview showed only one question. v2's checks only proved things rendered; **v3 is judged on whether it is actually good to use.** Every brief has a Quality bar: treat each line as a test you must pass and prove with a screenshot or an automated check.

## Design system (approved by the project owner on Oct 25, final; tokens live in ONE swappable theme file, `app/theme.css`)
The project owner rejected v2's "Calm Instrument" one-blue look (findings 06 §2 Direction A and its "no gradients / one accent" rules are REPLACED by this section; 06 §4 motion specs, §9 craft checklist, §10 accessibility and §15 pitfalls other than the color rules still apply).
- **References:** Linear (polish, motion, dark elevation from one hue), Raycast (vivid per-command color, crisp icons), Duolingo (session flow, progress bars, end-of-session moment), Notion (home and onboarding clarity). Name these in code comments of `app/theme.css`, not in the UI.
- **Tool color identities**, carried through each tool's icon, nav tab (active state), primary buttons, focus/highlights and illustration: **Check = warm coral**, **Tailor = green** (lean emerald/teal so it never reads as the risk "low" green), **Practice = violet**. Tracker and Profile use the ink/neutral brand color. Each accent has light + dark values, a soft tint (backgrounds) and an on-accent text color, all WCAG AA (text >= 4.5:1, UI marks >= 3:1).
- **Risk colors are reserved:** red (high), amber (medium), green (low) appear only on risk results (ring, level icon, tags, marks), always with an icon + words, never color alone. Coral must be visibly distinct from risk red (more orange/pink, lighter); if a report screen shows both, the report's chrome uses neutral, not coral.
- **Canvas:** warm off-white light theme (e.g. #FBF8F3 page, white cards, warm grey borders). Dark theme: deep ink-navy (e.g. #0D1220 page with 3-4 elevation steps derived from one hue), never pure black, no shadows in dark (use surface steps).
- **Type:** Bricolage Grotesque (display, headings; next/font/google, OFL) + Inter (body, UI; next/font/google). Tabular numbers on scores, counters, timers.
- **Depth and texture:** cards with gentle layered shadows (light theme), soft gradient mesh only in the home hero (and optionally faint on empty states), no glow borders, no blurred blobs everywhere, no emoji bullets.
- **Icons:** lucide-react only (one stroke width, 1.75 or 2 everywhere). **Illustrations:** one small hand-made SVG illustration per tool (Check, Tailor, Practice) plus one for Profile/empty states, drawn in the tool's colors, used on Home and empty states. Inline SVG components, no stock art, no AI-generated images.
- **Motion (motion/react, `MotionConfig reducedMotion="user"`):** page transitions between tabs (fast crossfade + 8px slide, <= 250ms), staggered card reveals on Home and lists (once, on mount; never scroll-reveal), score ring counts up on reveal, changed resume lines glow briefly when accepted/rejected, interview per-round progress bar, a small end-of-session celebration (tasteful, <= 1.2 s, no confetti flood; skip under reduced motion), hover/press states on cards and buttons. Under reduced motion everything is immediately in its final state.
- **Responsive:** designed (not just squeezed) at 390, 768 and 1440. Mobile: bottom tab bar with icons + labels, 44px touch targets, no sideways scroll at 320. Desktop: top nav (or left rail) with icons + labels; content widths that suit each screen (coding layout wide, forms narrow).
- **Copy:** short, second person, specific, verb first. No filler ("Unlock", "Supercharge", "Seamless"), no fake stats.

## What the project owner saw (v2) and what must change
Output was longer than the original, re-flowed into a new layout, full of AI phrasing; no loading state, no preview, no per-change control. The fix is a different product shape: **an editor of small, targeted suggestions applied in place to the user's own file**, not a resume generator.

## Items (commit each; flip any feature flag only when it passes gates)
R1. **Structure-preserving model.** Parse the uploaded resume into `{ sections: [{ heading, lines: [{ text, kind: "bullet" | "text" | "heading", pageIndex, box? }] }] , pageCount, source: "pdf" | "docx" | "text" }` keeping order, headings and line positions (PDF: pdfjs text items with coordinates/font size; DOCX: paragraph/run indices via jszip on `word/document.xml`). Round-trip test: parse -> render with zero edits -> same text, same section order, same page count.
R2. **Company- and role-aware plan.** Before suggesting edits, build a `TailorPlan`: keywords from the job posting (required vs preferred, reuse `keywordGap`), plus company/role guidance from `/api/intel` (`kind: "resume"`: what the company says it values, published resume tips, engineering-blog themes), shown as a short "What we'll emphasize" panel with source links. Intel is cached and capped; if limited, fall back to posting keywords only and say so in one line. No live calls in tests (mock).
R3. **Minimal targeted edits.** The model proposes at most ~6 edits (default 3-5), each rewriting ONE existing bullet toward the plan's keywords, never adding bullets, sections, skills, employers, numbers, tools or dates that aren't in the original (the user may add a skill they really have via an explicit "I have this" toggle on the keyword-gap chips, which is the only way new terms enter). Each edit's proposed text must be <= the original line's length + 10% and must fit the same rendered width (measure with the line's font size; reject or shorten otherwise). Deterministic post-checks, all client- and server-side (the v2 guard ran only in the browser; move it to a shared module used by the API route too):
   - fact guard: no new numbers, proper nouns, tools, employers, titles or dates vs the original resume + accepted user facts (extend `resumeGuard`);
   - **AI-tell filter:** ban list (spearheaded, leveraged, utilized, passionate, synergy, cutting-edge, dynamic, results-driven, orchestrated, seamlessly, robust, innovative, "proven track record", "in today's fast-paced", "drove/drive impact", "showcasing", "demonstrating"), max one em dash per resume and none added by edits, no buzzword stacking (>2 adjectives in a row), no change in tense/person style vs the user's own bullets, keep the user's bullet punctuation style (period or not);
   - edits that fail are dropped or regenerated once; the UI never shows a failing edit.
   Prompt (findings 03 §7): give the model the original bullet, its neighbors for voice, the target keywords and the plan; ask for a plain rewrite in the user's voice; temperature low; JSON out.
R4. **Render in the original format.**
   - DOCX: edit the original `document.xml` in place, replacing the text of the edited paragraphs while keeping the first run's formatting (font, size, bold/italic spans where possible); everything else byte-identical. Download is the user's own file with only those lines changed.
   - PDF: keep the original pages; for each accepted edit cover the original line's box (background color sampled or white) and draw the new text at the same position and size with the closest standard font (pdf-lib), shrinking font size at most 5% to fit, else reject the edit with "Too long for this line". Also offer DOCX/plain-text export if the user prefers.
   - **Length check (must fail loudly in tests):** output page count <= original page count (one page stays one page), no line overflows its original box, total characters <= original + 3%.
R5. **The flow and UI (in the Tailor tool's green identity, using setup's theme tokens and lucide icons).**
   1. Inputs: resume (from Profile if already uploaded, else upload here), job posting (paste or from the check report target), optional company/role (prefilled from the target).
   2. **Loading/progress state** with real steps ("Reading your resume", "Reading the job post", "Looking up <company>", "Drafting edits", "Checking facts and length"), each resolving to a real outcome; ~200ms show delay, no fake progress; Cancel works.
   3. **Review screen:** desktop side-by-side (left: list of suggested edits, each with before/after word diff, the keywords it adds, a one-line reason and Accept / Reject / Edit; right: live preview of the actual resume page with the changed lines highlighted); mobile stacks them with a Preview toggle. Accepting/rejecting updates the preview instantly (changed line glows briefly; reduced motion = no glow animation). "Edit" lets the user type their own wording, re-checked by the guard on blur. Keyword-gap chips show found/missing; toggling "I have this" can trigger one new suggestion.
   4. **Preview before download:** the preview is rendered from the same bytes that will be downloaded (PDF.js render of the generated PDF, or a DOCX->HTML preview of the generated DOCX). Download buttons are disabled until the preview has rendered; show page count + "Same length as your original" check.
   5. Empty state with the Tailor illustration slot (shell stream provides illustrations; use a placeholder component name `TailorIllustration` from `components/illustrations` if present, else a lucide icon) and one-line explanation of what Tailor does.
R6. **Tests and QA.** Vitest: parser round-trips, edit limits, guard (fact + AI-tell + length/width), DOCX in-place edit preserves everything else (zip entries other than document.xml byte-identical), PDF page count unchanged, API route enforces the guard server-side, intel fallback. Playwright (`qa/v3-resume-*.mjs`, mocked `/api/rewrite` and `/api/intel` via route interception): upload -> loading -> review -> accept 2, reject 1, edit 1 -> preview updates -> download; shots at 1440 and 390, light and dark, of: empty, loading, plan panel, review, accepted-with-glow, preview, too-long rejection, download ready.
R7. **One live check (allowed: max 3 live calls total, made-up resume + made-up posting, `.env.local` is NOT in your worktree, so skip live calls; leave them to integration).** Instead record in your summary exactly which live calls integration should make.

## Quality bar (each must be proven by a test or a screenshot you looked at)
- Tailored output page count <= original (one-page fixture stays one page) and no line overflows; total length within +3%.
- At most 6 edits, every edit rewrites an existing bullet; no new sections, bullets, numbers, tools, employers or dates (guard tests with adversarial model outputs).
- Zero banned AI-tell words in any shown edit; em dashes not increased; style (tense, punctuation) matches the original.
- DOCX output differs from the input only in the edited paragraphs.
- Loading state visible within 300ms of clicking Tailor; preview renders before download is enabled; accept/reject updates the preview in under 200ms (no network).
- Company plan panel cites at least one source link when intel returns, and degrades to "Using the job post only" when capped.
- Looks like a polished product at 390 and 1440 in both themes (you looked at every shot; fix anything cramped, clipped or default-looking).
